# Known issues

Honest status of what is verified, what is broken, and what was never exercised.

---

## 1. `--checkpoint latest` — resolved (was a bug in this repo's tooling, not in Isaac Lab)

**Status: fixed. Isaac Lab's own `isaaclab play --checkpoint latest` was never broken.**

An earlier version of `scripts/export_policy.py` raised:

```
ValueError: No compatible manifested run with a checkpoint was found in
'<IsaacLab>\logs\rsl_rl\g1_flat'. Run training with the current unified training entrypoint
before using '--checkpoint latest'.
```

Two mistakes in this repo's wrapper, both invisible because the resolver *silently* finds zero
compatible runs instead of reporting a mismatch:

1. **Task name not normalized.** Run manifests store `normalize_task_name(task)`, and
   `play_rsl_rl.py:88` correctly passes `task=normalize_task_name(args_cli.task)`. The wrapper passed
   the raw CLI task.
2. **`agent=None`.** `_compatible_runs` compares `manifest["metadata"]["agent"]` against the requested
   metadata. Manifests record `"agent": "rsl_rl_cfg_entry_point"`, so `agent=None` rejects every run.
   Measured: `metadata={"agent": None}` → **0 compatible runs**;
   `metadata={"agent": "rsl_rl_cfg_entry_point"}` → **11**.

The framework path was verified correct by source inspection (`play_rsl_rl.py:88-89`: the task is
normalized and `args_cli.agent` holds the entry point). Only `export_policy.py` needed fixing; it now
mirrors those two details and resolves `latest` to the newest checkpoint.

If you write your own resolver wrapper, note that a metadata mismatch produces an empty result rather
than an error — check `_compatible_runs` directly when debugging.

## 2. The only bundled motion is synthetic

`motions/g1_stand_synthetic.npz` is a 200-frame **stand-still clip** generated by forward kinematics
from the G1's default pose. It is format-valid and exercises `MotionLoader`, the command term, every
reward and termination, and the full RL loop — but it contains no motion, so no useful policy can be
trained from it.

Real training requires retargeted motion in the Unitree CSV convention (e.g. the LAFAN1 retargeting
dataset). See `RUNNING.md` section 6.

---

## 3. `csv_to_npz.py` is untested end to end

The migration fixed its quaternion reordering and its Windows-hostile hard-coded `/tmp/motion.npz`,
but the conversion itself was never run, because no source CSV is available on this machine. Treat it
as unverified.

It also still writes to a fixed path unless you pass `--output_file`.

## 4. Capsule conversion changes six collision shapes substantially

Six squat cylinders satisfy `L ≤ 2r`, so the capsule mapping degenerates them to spheres of the same
radius roughly twice the original volume:

```
r=0.073 L=0.064 | r=0.07 L=0.056 | r=0.065 L=0.04 | r=0.068 L=0.01 | r=0.05 L=0.05 (x2)
```

These are foot and hand pads, i.e. contact-critical parts. This matches what the Isaac Lab 2.x
importer did, so it is faithful to upstream — but it is a large geometric change. Use
`make_capsule_urdf.py --keep-squat-cylinders` to leave them as cylinders.

Not measured: whether either choice is better for the resulting policy.

---

## 5. W&B upload was never exercised against the cloud

The offline path is verified: `wandb.init(mode="offline")` + `upload_to_wandb()` completes, and the
artifact manifest contains both `policy.onnx` and `policy.onnx.data`. A live upload to a real project
was **not** performed — it needs credentials.

One bug was found and fixed during this testing: `Artifact.add_file(onnx_path)` alone omits the
external-weight sibling `policy.onnx.data`, producing an artifact that cannot be loaded. The upload
now globs `<onnx_path>*`.

## 5b. `--logger wandb` requires `wandb<0.29` (Isaac Lab 3.0 / wandb incompatibility)

Isaac Lab 3.0's `announce_new_run` (`isaaclab_rl/utils/wandb.py:107`) calls `wandb.util.generate_id()`.
**wandb removed that symbol in 0.29.0**, so enabling the W&B logger aborts before training starts:

```
AttributeError: module 'wandb.util' has no attribute 'generate_id'
```

Bisected removal point:

| wandb | `wandb.util.generate_id` |
|---|---|
| ≤ 0.28.0 | present |
| **0.29.0** | **removed** |
| 0.30.0 | removed |

`wandb.sdk.lib.runid.generate_id` still exists; only the `wandb.util` alias is gone. Isaac Lab declares
`wandb>=0.13.11` with no upper bound, so a current release resolves in and breaks the logger.

**This is a framework/dependency gap, not a project issue** — upstream never required W&B in a way
that touched this path. Three options, in order of preference:

1. **Pin the dependency:** `uv pip install ... "wandb==0.28.0"`. No code changes.
2. **Pre-set `WANDB_RUN_ID`:** `announce_new_run` only generates an id when the variable is unset, so
   setting it skips the failing branch. Costs you auto-generated run ids, but that id is also what
   `--checkpoint wandb:...` needs, so owning it is not a real loss.
3. **Patch Isaac Lab:** `wandb.util.generate_id()` → `wandb.sdk.lib.runid.generate_id()`. Requires
   reapplying on every framework upgrade, which is why pinning is preferred.

This repository pins option 1 in the environment, and README documents all three.

### Related: entity must be set via `WANDB_USERNAME`, not `WANDB_ENTITY`

| Location | Variable read |
|---|---|
| `resolve_wandb_entity` (prints the resume hint) | `WANDB_ENTITY` or `WANDB_USERNAME` |
| `WandbLogWriter` (the real `wandb.init`) | **only `WANDB_USERNAME`** |

Setting only `WANDB_ENTITY` makes the printed hint correct while the run silently lands under the
default entity. Use `WANDB_USERNAME`.

## 6. rsl_rl 2.x → 5.5.1 was not diffed at the library level

`check_agent_cfg_equivalence.py` proves that *this project's* agent configuration migrates to
identical values (55 fields, 6 benign differences). It does **not** prove the two library versions
compute the same gradients: no rsl_rl 2.x source was available to compare against. Treat PPO's
numerical behaviour as unverified.

Checkpoints saved by rsl_rl 2.x are also not loadable in 5.5.1 (the save dict keys changed).

---

## 7. The W&B registry motion channel is gone

Upstream pulled reference motions from a W&B artifact registry via `--registry_name` and linked the
training run to that artifact with `wandb.run.use_artifact(...)`. Isaac Lab 3.0 has no equivalent, so:

- motions must be local files, passed as `env.commands.motion.motion_file=<path>`
- a training run no longer records which motion artifact it came from

`export_policy.py --wandb_run_path` writes an `exported_from_run` field for export provenance, but
that is a substitute only for the export side.

---

## 8. In-training ONNX export is no longer automatic

Upstream's `MotionOnPolicyRunner.save()` exported a motion ONNX on **every** checkpoint and uploaded
it. In 3.0 the unified entrypoint has no such hook, so export is a deliberate separate step
(`scripts/export_policy.py`). A custom `--external_callback` or a runner wrapper could restore the
automatic behaviour; that was not implemented.

---

## 9. `num_envs` is 64, not 4096

Set for a 4 GB GPU. The upstream default needs roughly 16 GB of VRAM and 32 GB of RAM per the Isaac
Lab system requirements.

This is the largest behavioural difference in the whole migration and it is **not** an API artifact —
no amount of code correctness recovers the lost batch size. Paper-level results require appropriate
hardware.

---

## 10. Smaller carry-overs

- `scripts/replay_npz.py` and `csv_to_npz.py` still call the deprecated whole-state
  `write_root_state_to_sim` / `write_joint_state_to_sim` forwarders. They work and warn; they are off
  the train/play path and were not migrated.
- The upstream `scripts/rsl_rl/{train,play,cli_args}.py` and `utils/my_on_policy_runner.py` are dead
  code under 3.0 (`hydra_task_config` and `dump_pickle` no longer exist). They were left in place as
  reference but cannot run.
- `MotionOnPolicyRunner`'s custom metrics logging was not reimplemented. The 11 tracking-error metrics
  computed in `MotionCommand._update_metrics` may not reach the logs; unknown whether they did
  upstream either. Worth checking the TensorBoard curves.
- The G1 URDF importer logs `Stiffness and damping not available joint ...` during conversion. Gains
  come from `ImplicitActuatorCfg`, so this is cosmetic, but it was not confirmed to be harmless.
